## ADR-002: 采用 Access JWT + Refresh Opaque + Redis Session State + Event Audit + Key Rotation + MFA 的认证架构

**日期**: 2026-04-20  
**状态**: Accepted  
**上下文**: 项目将构建新一代云原生认证/授权体系，目标是在保持网关鉴权低延迟的同时，满足会话撤销、设备管理、审计追踪、密钥轮换与高风险场景增强认证需求。仅依赖长生命周期 JWT 难以兼顾安全治理与可追溯性，因此需要引入“无状态访问令牌 + 有状态会话控制 + 异步安全事件”的组合方案。  
**决策**:
- Access Token 采用短生命周期 JWT，由客户端持有，在网关和服务侧本地验签，默认不依赖数据库完成认证。
- Refresh Token 采用高熵 Opaque Token，仅服务端保存哈希与元数据，支持轮换、撤销与重放检测。
- Redis 作为会话状态中心，保存 `sessionId`、设备信息、撤销状态、最近刷新时间、MFA 状态及必要的例外控制信息。
- 登录、刷新、登出、撤销、失败登录、MFA 挑战与结果等安全行为统一发布为领域事件，并异步写入审计存储。
- JWT 签名采用支持 `kid` 的密钥版本机制，支持新旧密钥并存校验与平滑轮换。
- 管理端与高风险操作启用 MFA，并预留按角色、设备、风险等级触发的增强认证能力。
- 认证与授权分层：网关负责身份校验与粗粒度授权，业务服务负责租户边界、资源归属和领域权限判定。
**后果**:
- ✅ 鉴权主链路保持低延迟，大多数请求可实现本地验签、零数据库 IO。
- ✅ 会话撤销、单设备下线、改密失效、封禁控制与刷新治理具备服务端可控能力。
- ✅ 审计链路与主业务链路解耦，便于后续扩展风控、报表与合规能力。
- ✅ 支持逐步演进到 OAuth 2.1 / OIDC 最佳实践，并兼容 WebSocket 等长连接场景。
- ⚠️ 系统复杂度上升，需要统一设计 Redis Key、刷新轮换策略、事件模型与密钥治理流程。
- ⚠️ Refresh Token、MFA 与密钥轮换会增加实现与运维成本，需要分阶段落地。  
**实施阶段**:
- 第一阶段：补齐登录、刷新、登出与会话撤销主链路，统一 `sessionId` 作为身份与审计关联键。
- 第二阶段：落地 Redis 会话模型与 Refresh Token Rotation / Reuse Detection。
- 第三阶段：完善安全事件模型，异步落库并支撑查询与追踪。
- 第四阶段：引入 `kid`、多密钥并存校验与平滑轮换。
- 第五阶段：在管理端和敏感操作中启用 MFA，并为 Passkey / WebAuthn 预留演进空间。
