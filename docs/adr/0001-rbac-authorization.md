# ADR 0001：RBAC授权和动态导航

## 状态

接受

## 背景

管理服务需要基于角色的授权、动态导航和数据权限路径。该项目已经在用户、JWT声明和Redis会话记录中携带了“tenant_id”，但未启用查询时租户隔离。

## 决定

1. 介绍RBAC实体：“角色”、“权限”、“菜单”、“用户角色”和“角色权限”。
2. 使用稳定的权限代码，如`system:user:create`。API授权在后台强制执行，从不从菜单可见性推断。
3. 使用稳定的菜单代码，如“system.user”。前端拥有“代码->路由/组件”注册表。后端配置拥有菜单层次结构、标签、排序顺序、可见性和权限绑定。
4. 支持菜单类型“目录”、“内部”、“外部”和“IFRAME”。内部菜单可能只引用前端注册代码。外部和iframe URL必须是HTTPS，并由前端根据其允许的源策略进行验证。
5. 不要在第一阶段创建“角色菜单”关系。菜单根据调用者的有效功能权限进行筛选。
6. `super_admin`是一个仅用于数据库引导的角色。任何应用程序API都不能创建、更新、分配、撤销或删除它。具有此角色的用户将绕过函数、菜单、数据范围和未来租户限制。
7. `system_admin`是可编辑的默认角色。每个公开注册的管理员在用户创建后都会被事务性地分配此角色。
8. 第一期有效权限直接从 RBAC 持久化层查询，因此角色和权限变更会在下一次请求立即生效。后续 Redis 缓存必须由 security framework 提供抽象，而不是由 system 模块直接引入 Lettuce；缓存 TTL 不得超过 30 分钟，写入变更时必须主动失效。JWT 仅存储身份/会话数据，不存储有效权限集。
9. RBAC表保留“tenant_id”，默认值为“0”，而实际的租户查询隔离仍然是一个单独的未来决定。
10. 在第一阶段，数据权限仅限于模型和服务扩展点。字段权限被推迟，直到存在具体要求。

## 后果

- 操作人员可以在不进行前端部署的情况下重新组织和授权现有菜单。
- 添加内部页面仍然需要前端实现和注册；未知的内部菜单代码是配置错误，不得触发动态模块执行。
- 即使客户端操纵导航状态，后端授权仍然有效。
- `super_admin`恢复和分配是经过深思熟虑的数据库操作，需要部署/runbook控制。
- 第一期无授权缓存，变更在下一请求生效；后续缓存实现以 30 分钟作为故障回退界限。
